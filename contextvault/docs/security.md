# Security and privacy

## Isolation

Each route authenticates a database-backed opaque session and authorizes ownership server-side. Retrieval independently verifies the selected collection, and both vector and lexical SQL include owner, collection, ready status and archive constraints. Vector SQL additionally constrains embedding model; lexical text search does not compare embeddings. Composite foreign keys prevent associating a document with another owner's collection, and cascading deletes remove chunks. Conversation reads are owner-scoped; source previews additionally require the source to remain ready, unarchived and in the conversation collection. Before persisting a chat answer or returning playground/comparison evidence, the server locks and rechecks its retrieved evidence; a scope or content change causes a conflict rather than returning the stale snapshot. Data already sent to a provider before a concurrent change cannot be recalled.

The schema enables and forces RLS on owned tables. Every owned operation uses a transaction and `set_config('app.user_id', ..., true)` so the tenant context is local to that transaction. Integration tests use a `NOSUPERUSER NOBYPASSRLS` role to verify a query without an owner `WHERE` cannot read another user's rows. PGlite's default superuser bypasses RLS, so the demo relies on the additional application filters; do not use that superuser setup for a multi-user deployment. Migrate under a separate owner and run the application and worker with a non-owner, non-superuser, non-BYPASSRLS role. The role can set the application context, so RLS is defense against missing filters, not a defense against an attacker who controls the application role or arbitrary SQL. Session/user tables are accessed only by trusted auth/worker code and do not have tenant RLS.

## Authentication and request safety

Passwords are scrypt-hashed with random salts; session tokens are random, stored hashed, expire after 30 days, and are delivered in HttpOnly, SameSite=Lax cookies (Secure in production). Login/registration/upload/chat have database-backed fixed-window limits. State-changing browser requests are checked against same-origin headers; configure the reverse proxy to overwrite forwarded host/IP headers. Cookies require HTTPS in production. This custom account implementation lacks MFA, verified email, password reset, session management UI, advanced abuse controls and an independent security audit. Use a mature identity provider before sensitive production use.

Uploads are untrusted: filename, size, extension, declared type and signatures are checked, text must be UTF-8, DOCX archive metadata is limited, PDF page count is capped, files are never executed, and downloads are authorized attachments with `nosniff`. This is not a malware scanner or a sandbox; use a dedicated isolated worker with resource limits, network restrictions and malware scanning. Text-based PDF extraction cannot read image-only scans. PDF and DOCX parsers are third-party dependencies that must be kept patched.

## Prompt injection and data disclosure

Documents can include hostile instructions. They are serialized as untrusted evidence, separate from the system prompt; the mock also avoids echoing obvious injection instructions. These measures reduce risk but **do not guarantee immunity**. Models have no tools or direct database access here. Citation label validation cannot establish semantic faithfulness. Always inspect the evidence.

Default mock providers run locally; no documents are transmitted to an external AI service. Explicit OpenAI or self-hosted endpoint configuration transmits chunks/questions to that endpoint. Review provider retention, regional processing, credentials, TLS and data agreements. The Settings page identifies the selected providers; a shared demo warns against private uploads. Do not put keys in browser code or logs. No automatic retention policy exists; delete documents/conversations manually and apply lifecycle rules to database backups and object storage. Conversation answers can retain excerpts after a source is moved, archived, reprocessed or deleted. Prior assistant messages are not included in later model prompts, although prior user-authored questions are. Previously sent provider requests cannot be recalled; delete relevant conversations separately when needed.

For production, add CSP/security headers at the reverse proxy, restrict embedding origins as appropriate, rotate secrets, monitor outbox failures and audit events, enable backups, and conduct authorization, dependency and penetration testing. Do not treat local demo settings as a production configuration.
